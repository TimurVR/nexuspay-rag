# Регламент работы с Git и процесс релизов

**Версия документа:** 1.9  
**Владелец:** Platform-SRE  
**Связанные документы:** `02_onboarding_guide.md`, `08_incident_management.md`

## 1. Ветвление (Trunk-Based Development)
Мы используем модифицированный **Trunk-Based Development**:
* `main` — основная ветка, всегда готова к деплою в production. Прямые коммиты в `main` запрещены.
* Ветки задач создаются от `main` по шаблону: `feat/NP-1234-short-desc` или `fix/NP-1234-bug-name`.
* Время жизни feature-ветки не должно превышать **3 рабочих дня**.

## 2. Требования к Merge Request (MR)
Для влития MR в `main` должны быть выполнены 4 условия:
1. Успешное прохождение CI-пайплайна (линтеры `golangci-lint`, unit-тесты, покрытие нового кода не ниже **80%**).
2. Отсутствие критических уязвимостей по результатам сканирования **Trivy** и **SonarQube**.
3. Минимум **2 апрува** от участников команды (один из них должен быть от Senior-разработчика или тимлида).
4. Сообщения коммитов оформлены по спецификации **Conventional Commits**.

## 3. Релизное окно и выкатка
* Деплой в **Staging** происходит автоматически после мержа в `main`.
* Деплой в **Production** выполняется по стратегии **Canary Deployment** (10% -> 50% -> 100% трафика с интервалом 15 минут).
* **Релизные окна:** понедельник – четверг с **10:00 до 17:00 МСК**.
* **Code Freeze (заморозка релизов):** по пятницам, в выходные и праздничные дни выкатка в production запрещена, за исключением критических хотфиксов (`hotfix/*`), согласованных с дежурным SRE.
